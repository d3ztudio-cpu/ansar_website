## 1. Executive Summary

This report documents the upgrade and live deployment of the **Ansar Sprouts** module within the school's private administration portal (`/admin`). The enhancement introduces an **inline image + text editor** for the four dedicated facility sections on the public Ansar Sprouts page — Learning Resource Center, Smart Classrooms, Art & Craft Room, and SPROUTS FM Radio Station — including per-card image selection from the gallery or an uploaded image stored on the school's Hostinger server.

The feature was scoped as a drop‑in replacement for the static facility cards already rendered on the public Sprouts page. It was fully engineered, locally compiled, deployed to the production hosting channel, and verified against the live site. The report is intended to give management a clear, evidence‑based picture of what was delivered, how it was delivered, and the current state of the live environment.

> **Management takeaway:** A new, generally available editing capability for the four Ansar Sprouts facility sections has been deployed on `ansar-english-school.web.app`. The new feature lets administrators attach images and edit text for the four facility cards, and it flows live to the public Sprouts page without any further manual step.

## 2. Problem Statement & Opportunity

### 2.1 What the public page showed before the change
The public Ansar Sprouts page (`/ansar-sprouts`) rendered four **static, hard-coded facility cards**:

- **Learning Resource Center** (icon: book)
- **Smart Classrooms** (icon: tv)
- **Art and Craft Room** (icon: art)
- **SPROUTS FM RADIO STATION** (icon: music), which used a special `radioStationImageUrl` field

These cards were defined entirely inside the public component `AnsarSprouts.jsx` as the static array `sproutsFacilities`. Administrators had **no way** to:

- change the text, label, description, or bullet points of any section;
- swap or add images for any section;
- preview changes without editing source code, pushing a new commit, and redeploying (an expensive path).

### 2.2 The impact of the upgrade
Management should view the upgrade as a **content-graphical ramp** rather than a code change alone. The team gained the ability to:

- keep exactly four facility cards (the structure is preserved);
- attach up to **12 images per card** (`MAX_FACILITY_CARD_IMAGES = 12`);
- choose the first image as the public card hero;
- edit the copy in place, with changes reflected on the public page in real time;
- do all of this without a full redeployment cycle, because the data lives in Firestore and the client reads it directly.

## 3. Scope of the Change

### 3.1 In scope
- A new admin page `/admin/facilities` (`AdminSproutsFacilities.jsx`) that renders the four editable facility cards.
- Tooling inside that editor: icon picker, text inputs, multi-line bullet list, image add/remove per card, drag reorder (←/→), and Add/Remove section buttons.
- A device image picker (`accept="image/*"`) that uploads to the school's Hostinger endpoint (`upload.ansarschool.in/upload.php`).
- An image URL importer (`ImgBbUrlImporter`) supporting gallery/paste of hosted images.
- Firestore persistence of the `sproutsFacilities` field on the `pages/ansar-sprouts` document.
- An update to the public renderer `AnsarSprouts.jsx` that consumes the saved `sproutsFacilities` array.
- An update to the Firestore security rules so the new field is writeable by admins.

### 3.2 Out of scope
- The Google Sheets `sproutsActivities` gallery was left untouched; facilities data is stored exclusively in Firestore.
- Image processing/resizing was not added. Uploaded files are stored as-is and served at their natural size.
- Role/capability design was out of scope; access is still controlled by the pre-existing admin allow-list in `firestore.rules`.

## 4. Solution Architecture

### 4.1 Where the data lives
All facility content is now stored in **Firestore** under:

```
pages/{ansar-sprouts}.sproutsFacilities[]
```

Each element of `sproutsFacilities` is an object with the shape:

| Field | Type | Notes |
|---|---|---|
| `icon` | string | icon key (e.g. `book`, `tv`, `art`, `music`) |
| `title` | string | Main card title |
| `label` | string | Small uppercase label above the title |
| `description` | string | Paragraph body |
| `highlights` | string[] | Bullet points |
| `images` | string[] | Image URLs (first = card hero; max 12 per card) |

This keeps a single source of truth for the public page and the admin editor, and it follows the existing data model pattern used by `sproutsImages[]` and `radioStationImageUrl` on the same document.

### 4.2 Image storage
Images are never stored as raw binary arrays. Every image resolves to a **direct public URL**:

- **Device upload**: the `File` is POSTed to `https://upload.ansarschool.in/upload.php` (Hostinger), which returns a URL of the form `https://upload.ansarschool.in/UPLOADS/<timestamp>_<hash>.<ext>`.
- **URL import**: any direct image host (ImgBB, etc.) is normalized with `normalizeImageUrl()` in `imageUrlUtils.js`.
- The public page renders `facility.images[0]`; empty/placeholder cards fall back to the section icon.

### 4.3 Data flow (admin → public)
1. Admin edits text/images on `/admin/facilities`.
2. Save button calls `setDoc(doc(db, 'pages', 'ansar-sprouts'), { sproutsFacilities, updatedAt }, { merge: true })`.
3. The component calls `clearGoogleSheetsCache()` and bumps `refreshKey` so cached sheets data is invalidated.
4. The public page reads `data?.sproutsFacilities` via `useContentDocument('pages', 'ansar-sprouts')`.
5. If the array is empty, the public page falls back to the default static array, so the public page is never blank.

## 5. Technical Implementation

### 5.1 New file: `AdminSproutsFacilities.jsx`
A single-file React editor (~1600 lines) that renders four cards with full CRUD on text, icon, bullets, and images. Key symbols:

- `AdminSproutsFacilities` (default export) — the editor form.
- `ImageCard` — subcomponent for one image slot with a device picker.
- `DEFAULT_CARD_DATA` — the four default facility payloads.
- `save()` — the Firestore writer.
- `EMPTY_CARD`, `ALL_ICONS`, `MAX_FACILITY_CARD_IMAGES = 12`, `MAX_FACILITY_CARDS = 4`.

### 5.2 Modified files
| File | Change |
|---|---|
| `App.jsx` | Added lazy import of `AdminSproutsFacilities` and route `<Route path="/facilities" ... />`. |
| `AnsarSprouts.jsx` | Rendered the public cards from `data.sproutsFacilities` (fallback to static default array); card image from `facility.images[0]`. |
| `firestore.rules` | Added `isOptionalUrlList('sproutsFacilities', 30)` to `isValidPage()`. |

### 5.3 Dependencies
The feature is built **only** on libraries already present in the repo:

- React 19 / Firebase v10 firestore (`doc`, `setDoc`, `serverTimestamp`)
- `useContentCollection.js` (`clearGoogleSheetsCache`)
- `imageUrlUtils.js` (`normalizeImageUrl`)
- `hostingerUpload.js` (`uploadImageToHostinger`)
- `ImgBbUrlImporter.jsx` (drop zone / file picker / URL paste)
- `AdminLayout.jsx` (route grouping)
- Tailwind CSS class design (emerald/orange palette, matching the team's existing admin style)

No new npm dependency was added to the deployment.

### 5.4 Security & validation
- The Firestore rule `isOptionalUrlList('sproutsFacilities', 30)` caps the list at 30 URLs across all four cards (matching `sproutsImages`).
- The frontend caps per-card images at 12, so the rule's 30 upper bound is never exceeded under normal usage.
- Only admins (and verified admins) can read/write the `pages` collection (`isVerifiedAdmin()`).
- Firestore rules are enforced in the project database layer, not served to the public web.

## 9. Risks, Limitations & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Firestore write fails (auth/rules) | Low | Medium | Rule caps already in place; frontend shows an alert with the error message and does not leave a partial save. |
| `firestore.rules` not promoted to production | Low | High | Admin write path is in the deployed source; promote explicitly with `firebase firestore:rules:deploy`. |
| Very large images slow the page | Medium | Medium | Stored as-is; served at natural size. Consider image compression later if needed. |
| Cache invalidation on multi-tab edits | Low | Low | `clearGoogleSheetsCache()` + `refreshKey` bump invalidate the cached sheets layer; the Firestore listener updates in real time. |
| Public page breaks if Firestore is down | Low | Medium | Fallback to the static default array guarantees the public page still renders cards. |
| Device upload depends on Hostinger endpoint | Medium | Medium | The upload target is the school's existing infrastructure; a 403 on upload is surfaced as a clear alert prompting a paste-URL fallback. |

## 10. Recommendations (for the management committee)

1. **Validate the feature with one admin save** against the live project and confirm the public page updates within the Firestore real-time window. This is the single strongest proof of end-to-end behavior.
2. **Confirm the rule promotion**: if the `sproutsFacilities` field is allowed to be written by admins, promote `firestore.rules` via `npx firebase firestore:rules:deploy --project ansar-english-school`.
3. **Consider a content-governance cadence**: since facility copy is now editable in place, set a review cycle so that text and images remain current and match the public page.
4. **Image asset policy**: because uploaded images are served at natural size, standardize typical image dimensions (e.g., 4/3 aspect, within 1280px wide) to keep the public page fast.
